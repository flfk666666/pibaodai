# 本地能力库：读取、核验与回写

首次定位库、遇到资料缺失/过期或回写时读取。本库保存可核查的能力事实，帮助选路线；详细教程以官方手册和执行窗口为准。

## 找到两个不同的落点

**通用库：** 优先沿用当前项目已配置的位置；否则在可写用户项目下使用 `tech-capabilities/`。只有明确配置或目录存在时才说已经有库。包内 `seed/` 是有日期的只读起点，不在安装目录内写入使用数据。

**私人交接：** 优先使用项目已有私人目录，并实际核实该路径被 Git 忽略。没有受保护路径时，使用仓库外、安装目录外的用户私人数据目录。无法确定或不能写入时，先输出精简交接文本；不要把它临时放到公开仓库等以后再清理。

在 Git 项目可用 `git -C <项目根> check-ignore -- <交接相对路径>` 检查忽略规则；没有该工具时不能宣称已检查。仅在该 Git 项目中有效的忽略规则不代表另一个项目也安全。

```text
tech-capabilities/
├── index.md
└── entries/<id>.md

已核实被忽略或在仓库外的私人数据目录/
└── handoffs/<task-id>.md
```

无文件工具、无可写目录或写入失败时，继续完成能做的规划，给出待保存内容与缺口。未完成写入不得声称“已入库”。

## 读取与条目粒度

先读本地 `index.md`，按能力标签和任务检索，只读相关条目；本地没有再按需看种子。每个条目描述“一个产品/模块的一组相关能力”，一个产品可有多个条目，同一能力可关联多个产品。

索引保持紧凑：能力/关键词、条目 ID、相对链接、证据状态。私人成果不进入公共索引。ID 使用小写英文、数字与连字符；新建前检查已有条目，避免别名导致重复。

条目参考格式（字段名保持一致，未知值用 `null`；以下仅为格式说明，不是已核实产品记录）：

```yaml
id: product-capability
product: Product name
module: Relevant product module
capabilities: [capability-tag]
interface: web-or-desktop-or-api
evidence_status: lead
checked_at: null
source_published_at: null
```

正文至少包含：

- **能力与用途**：做什么、输出什么、适用条件和与其他步骤的衔接。
- **重要限制**：设备、地区/账户、费用或部署条件。只写已核实事实，未知的直接说明。
- **来源**：官方入口、有关功能的文档/源码链接；每个重要能力结论应能对应来源。
- **核验说明**：何时实际读到什么、读取失败之处、是否只看文档、是否有账户实测。
- **待核实项**：哪些条件会改变当前推荐，需要在使用前核对。
- **使用反馈**（有才写）：使用日期、环境/任务范围、实际结果与失败条件；不把单次成功推广为整款产品都验证过。

`evidence_status` 使用 `lead`（仅线索）、`documented`（资料正文支持）或 `observed`（实际任务有观察结果）。具体实测范围仍须看正文，不能只凭状态或日期选工具。用户反馈注明用户提供，不能改写成助手亲测。

## 本地命中后的时效判断

1. 明确这次选路线依赖的事实：例如能否接入某系统、某地区能否注册、预算是否够。
2. 核对条目来源是否支持该事实，日期与条件是否适用；索引命中本身不能替代检查。
3. 对价格、免费额度、地区、套餐、模型版本、接口限制和新功能开放状态等关键易变信息，按当次问题查证。稳定的能力背景可以带日期复用。
4. 出现冲突、旧版本、来源不完整或用户要求最新能力时，补查相关缺口。不要机械地每隔固定天数把所有条目作废，也不要全量刷新整个库。

`checked_at` 是实际查阅来源并确认正文支持记录之日；复制种子、使用条目或确认链接可打开不刷新该日期。只读到搜索摘要、空页面或登录墙时，保留 `lead` 和 `checked_at: null`，正文写实际尝试日期及失败情况。

## 有缺口时怎样调研

- 用“所需能力＋使用条件”检索，优先官方产品说明、功能文档、更新日志、一手源码。社区文章可发现线索，但关键结论要回到可靠来源。
- 实际打开对应材料再记录。注意端、模块、版本、地区和套餐区别；品牌名相同不意味着功能一致。
- 宣传、功能演示、文档支持、用户账户可用、实际任务有效，分别注明。不因官网写着能做，就声称已实测可用。
- 资料无法读取时保留读取限制，换可靠来源或给条件式方案。无法联网时复用有日期的背景，列待查项；不制造当天价格或最新功能。
- 只保存足以支持本次选择的摘要与链接，不搬运整本手册，不先建设全部产业清单。

## 怎样回写而不污染知识

1. 读取当前条目，核对 ID、产品/模块和已有来源。写入前若文件有新变化，重新合并，保留他人新增内容。
2. 合并本轮有依据的新事实，保留仍适用限制；冲突写清来源及日期，未核实的不覆盖为确定结论。
3. 只有实际查阅支持结论时更新对应核验日期；用户报告的成功另记为带日期的使用反馈。
4. 新条目写入成功后再登记相对索引链接，回读路径与链接；两步部分失败时说明哪些已保存，不报整体成功。
5. 只有通用事实进入条目。私人输入、账户、路径、截图、律师个案材料或交接内容留在私人位置。

复制种子时保留源日期、证据状态和限制，不覆盖较新的本地内容。保存通用条目不代表授权推送公开仓库。

执行交接要指明具体库路径、有关条目路径和私人交接路径。执行窗口回填实际结果、失败条件与观察日期；可复用的新事实才进入通用条目。没有实际反馈，不生成“亲测成功”。
