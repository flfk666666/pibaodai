# 分段澄清参考

先弄清用户想得到什么，再补影响选择的条件，最后收束本次范围。阶段是判断顺序，不是必须填完的问卷。

## 提问前先提取已有信息

- 从当前对话提取使用者、实际问题、期望结果、当前卡点和已给出的条件。
- 优先采用用户最新的明确表述；中途纠正覆盖旧理解，并同步修改后续拆解。
- 用户明确想学习某款产品时，把学习目标保留为约束，不能擅自改成只求最快产出。
- 判断缺口是否会改变路线。已知答案不重问，与当前选择无关的细节留给执行窗口。
- 一次只问一个关键问题。可给少量易懂选项，同时接受自由回答或“不知道”。
- 不按固定轮数提问，不要求框架打分，也不在每段末尾要求回复“确认”。

## 先理解想得到的结果

必要时用一句话复述理解，然后问最能区分方向的缺口。先问现实结果，避免让普通用户先决定模型、平台或工作流。

可依次判断：用户要解决什么困扰，结果给谁用，怎样看得出有帮助。只补当前缺失且影响方向的一项。
若用户还说不清问题，先帮助辨认最困扰的具体场景；不要立即替其确定要做网站、视频或 Agent。
若用户同时提出多个目标，先厘清这次最想推进哪一个，不把其他目标自动删除。

以下均为编写示例，用来说明提问方式，不代表真实用户的选择：

| 用户原话 | 当前最有价值的一问 | 为什么先问 |
| --- | --- | --- |
| 我想做 AI 短剧 | 这次更想先做出一条试看片，还是建立能重复制作的流程？ | 两种结果需要不同的拆解范围 |
| 我想学一个工作流平台 | 你最想用它完成哪件具体小事？ | 保留学习目标，同时找到可实践的结果 |
| 最近工作太乱，想用 AI | 最近哪件反复发生的事最让你费时间？ | 先辨认问题，再判断是否需要工具 |

## 再补会影响方案的条件

只在结果方向足够清楚后补关键条件。按任务挑选，不整表盘问。

| 条件 | 什么时候值得问 |
| --- | --- |
| 设备、系统、网络或账号访问 | 决定候选产品是否能用，或在线与本地路线是否可行 |
| 预算、可投入时间、完成期限 | 决定收费方案、工作量或本次产物规模 |
| 已有材料与格式 | 决定能否复用输入、需要补什么以及步骤能否衔接 |
| 技术熟悉程度、操作偏好 | 决定网页、客户端、配置工具或代码路线的门槛 |
| 使用频率、后续维护意愿 | 决定一次性处理还是值得建立可复用流程 |
| 数据处理要求 | 决定材料能否交给外部服务及候选路线的边界 |
| 所在地区或专业人员参与 | 现实事务依赖当地条件或专业判断时，决定资料准备与接手方式 |

解释问题与选择的关系即可，例如“这会决定是否需要本地处理”。不要用术语测试用户。
用户不知道答案时，判断能否保留分支；可逆且不影响当前首选的临时假设可以先用，但要明确标注。
尚未回答且足以改变首选路线的问题继续逐项问；未回答不是默认同意。
暂时不影响选择的资料缺口记入交接，不因追求信息齐全而延长对话。

## 收束本次范围与停止追问

用简短的“本次目标／已知条件／待定事项”归纳理解，将大目标切成一个可交接的阶段。
阶段应有可观察的产物或变化，并能说明从哪里开始、怎样判断做到；不要擅自把长期目标改小。
当信息已足够时，直接进入能力拆解，不为展示阶段而再提问。

同时满足以下条件就停止追问：

- 能列出本阶段需要的能力、主要输入和前后依赖。
- 能比较合理路线，且保留用户已选定的目标与约束。
- 没有尚未回答、足以改变首选路线的关键问题。

之后出现新纠正或关键证据时，更新理解与路线；只补新产生的关键缺口，不重跑整套问答。

## 保留事实、假设与证据的区别

| 类型 | 记录方式 |
| --- | --- |
| 用户已确认 | 写明用户实际说过的目标、条件或选择；不把示例、沉默和助手推断写成用户事实 |
| 临时假设 | 写明假设内容、采用原因及可能影响；条件变化时重新判断 |
| 外部证据 | 指向实际读取的来源或能力条目，保留核验日期与支持范围；资料支持不等于用户账号已可用 |
| 未知或冲突 | 明确待核实内容、是否影响路线，以及交给当前问答还是执行窗口处理 |

进入能力匹配时，只带走本阶段目标、已知约束、必要假设和未决项。用这些信息判断各步适合 AI、现成软件、普通自动化还是专业人员，再找具体产品。
